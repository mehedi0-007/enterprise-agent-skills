# Query Optimization

## Core Rule
Optimize from evidence, not intuition.

A query being "complex" does not prove it is slow, and an index being possible does not prove it is useful.

## Workflow
1. Identify the real workload and representative parameters.
2. Measure current latency/throughput.
3. Inspect the SQL generated by the application.
4. Run EXPLAIN.
5. Use EXPLAIN ANALYZE when safe and appropriate.
6. Compare estimated vs actual rows.
7. Inspect scan types, joins, sorting, filtering, memory/buffers, and time.
8. Identify the bottleneck.
9. Make the smallest high-confidence change.
10. Re-measure.
11. Verify result correctness and concurrency behavior.

PostgreSQL's EXPLAIN shows the planner's chosen scans and join algorithms; EXPLAIN ANALYZE executes the statement and reports actual behavior, so use it carefully for mutating statements. 

## Common Root Causes
Investigate:
- missing or unsuitable index
- low-selectivity index
- poor composite-index order
- stale statistics
- accidental sequential scan on large data
- inefficient joins
- unnecessary sorting
- large result sets
- over-fetching
- N+1 application queries
- functions/casts preventing useful index use
- expensive aggregation
- repeated queries that should be combined/cached

## N+1
If one request executes one query for a collection and then one query per item, treat it as suspicious. Consider a join, batched query, eager-loading strategy, or explicit data loader appropriate to the ORM.

## Pagination
Never let an API expose an unbounded large collection.
For large/changing datasets, evaluate keyset/cursor pagination instead of deep OFFSET scans.

## Caching
Only add caching when:
- the data is expensive enough to justify it
- staleness is acceptable and defined
- invalidation is understood
- cache key cardinality is controlled
- failure falls back safely

Caching a badly understood query can hide the real problem and introduce consistency bugs.

## Verification
Record before/after evidence:
- latency
- rows examined/returned
- execution plan
- resource usage where available
- correctness
- impact on writes/index maintenance
