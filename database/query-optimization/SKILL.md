# Query Optimization — Production Playbook

## 1. Mission

Optimize the actual bottleneck while preserving correctness.

Never equate:
- "complex SQL" with "slow SQL"
- "sequential scan" with "bad plan"
- "index exists" with "fast query"
- "cache added" with "performance fixed"

PostgreSQL uses a cost-based planner to choose plans based on query structure and table statistics. `EXPLAIN` shows the chosen plan; `EXPLAIN ANALYZE` executes the statement and reports actual behavior. citeturn851007search3turn851007search5

---

## 2. Activation

Use this skill when:
- endpoint/query latency is above target
- DB CPU/I/O is elevated
- p95/p99 latency regresses
- a query appears in a hot path
- an N+1 pattern is suspected
- a collection returns excessive rows/data
- a deployment changes query behavior
- indexes are being proposed as a performance fix

Do not optimize merely because a query "looks ugly."

---

## 3. Establish the Workload

Before changing SQL, identify:
- exact query
- representative parameters
- table/data volume
- execution frequency
- concurrent load
- latency distribution
- rows returned
- bytes transferred where available
- current indexes
- recent schema/data changes

A query that is fast on a developer laptop with 1,000 rows may fail at production cardinality.

---

## 4. Baseline

Record enough evidence to compare before/after:
- p50/p95/p99 when available
- execution time
- planning time where relevant
- rows returned
- query count/request
- DB CPU/I/O
- memory
- network/egress for large results

For repeated production queries, `pg_stat_statements` can help identify high-frequency or expensive query patterns. Neon specifically recommends using it when diagnosing data-transfer/egress-heavy query workloads. citeturn851007search7

---

## 5. Diagnostic Workflow

```text
Observed slowdown
      ↓
Identify real workload
      ↓
Measure baseline
      ↓
Inspect SQL generated by application
      ↓
EXPLAIN
      ↓
EXPLAIN ANALYZE when safe
      ↓
Compare estimated vs actual rows
      ↓
Inspect scans / joins / sorts / aggregates / loops / buffers
      ↓
Check application query count and result size
      ↓
Identify dominant bottleneck
      ↓
Choose smallest high-confidence change
      ↓
Re-measure
      ↓
Verify correctness + write/operational impact
```

Do not change several unrelated things at once if you need to know which change helped.

---

## 6. EXPLAIN Reading

Inspect:
- estimated rows
- actual rows
- loops
- node execution time
- scan type
- join strategy
- sort/aggregate behavior
- buffer usage where available
- planning vs execution time

A large estimated-vs-actual row difference is important. It can point to stale statistics, skew, correlated predicates, or a query shape the planner estimates poorly. PostgreSQL's planner relies heavily on statistics to estimate cardinalities and calculate costs. citeturn851007search10

### Important
Do not optimize to remove a node type merely because it sounds expensive.

---

## 7. Sequential Scans

A sequential scan is not automatically a bug.

It may be appropriate when:
- the table is small
- the query returns a large percentage of rows
- reading the table sequentially is cheaper than random index access

Investigate when:
- the table is large
- the predicate is highly selective
- the query is unexpectedly scanning most rows

Ask why the planner chose it before adding an index.

---

## 8. Index Scans / Bitmap Scans

An index is useful only when the access pattern and data distribution make it cheaper overall.

Review:
- selectivity
- predicate shape
- ordering
- table size
- existing indexes
- heap fetch cost
- write/update overhead

Bitmap scans can be useful when many rows match and PostgreSQL benefits from combining index filtering with heap access.

Do not force an index plan merely because one exists.

---

## 9. Join Optimization

Inspect:
- join order
- join cardinality
- estimated vs actual rows
- number of loops
- inner-side lookup cost
- duplicate row multiplication

### Nested Loop

Can be excellent when:
- outer side is small
- inner lookup is cheap/indexed

Suspicious when:
- loop count is huge
- inner work is repeated expensively

### Hash Join

Often useful for equality joins when the inputs/memory make hashing effective.

Watch for:
- unexpectedly large inputs
- memory pressure/spilling where visible

### Merge Join

Useful when sorted inputs/order make it efficient.

Do not force join types before understanding why the planner chose one.

---

## 10. Cardinality Errors

One of the most valuable signals is:

```text
estimated rows ≠ actual rows
```

Large errors can lead to:
- wrong join strategy
- wrong join order
- inappropriate scan
- excessive memory/sort expectations

Possible causes:
- stale statistics
- data skew
- correlated columns
- parameter-sensitive distributions
- insufficient statistics detail
- complex predicates

Before rewriting SQL or forcing planner settings, inspect statistics and data distribution.

PostgreSQL supports extended/multivariate statistics for cases where single-column statistics are insufficient to model relationships between columns. citeturn851007search10

---

## 11. ANALYZE / Statistics

When data distributions have changed substantially, stale statistics can cause poor plan choices.

PostgreSQL documents `ANALYZE` as collecting table statistics used by the planner; autovacuum normally manages this, but substantial data changes can justify manual analysis. citeturn851007search13

Do not treat:

```text
query slow → run ANALYZE
```

as a universal fix.

First confirm that statistics are stale/problematic and that the plan reflects incorrect estimates.

---

## 12. Application-Level N+1

A query can be individually fast and still make a request slow because the application executes it hundreds of times.

Suspicious pattern:

```text
1 query → 100 users
100 queries → user orders
```

Possible fixes:
- join
- batch query
- intentional eager relation load
- data loader
- read model

But avoid replacing N+1 with a giant join that multiplies rows and transfers far more data than the UI needs.

---

## 13. Over-Fetching

Do not select data merely because the ORM makes it easy.

Neon specifically identifies fetching columns the application never uses and unbounded result sets as common causes of unnecessary Postgres data transfer. citeturn851007search7

Prefer explicit projections:

```sql
SELECT id, name, price
FROM products
...
```

instead of:

```sql
SELECT *
```

especially when rows contain:
- large JSON
- text/blob-like fields
- internal metadata
- sensitive columns

---

## 14. Unbounded Results

Any production collection should have an intentional bound.

Review:
- missing LIMIT
- excessive page size
- huge `IN` lists
- full-table application reads
- large exports executed synchronously

If a legitimate export requires large volume, use a dedicated asynchronous/export workflow rather than pretending a normal API request is a bulk-transfer mechanism.

---

## 15. Pagination Performance

Offset pagination can become increasingly expensive for deep pages because the database may still need to walk past skipped rows.

For large/high-churn datasets, consider keyset/cursor pagination.

Example concept:

```text
ORDER BY created_at DESC, id DESC
WHERE
  (created_at, id) < (:cursorCreatedAt, :cursorId)
LIMIT 50
```

A cursor design must have:
- stable ordering
- supporting index
- opaque client cursor
- defined behavior when data changes

Do not switch to cursor pagination merely because it sounds faster; verify the workload and UX requirements.

---

## 16. Sorting

Large sorts can dominate execution.

Ask:
- Can an existing index support the required order?
- Is the sort applied before filtering unnecessarily?
- Is the requested order selective/useful?
- Is the dataset too large for an interactive operation?
- Should the API allow arbitrary sorting at all?

Do not expose dozens of arbitrary sort fields without considering their database cost.

---

## 17. Filtering and Sargability

A predicate may prevent useful index usage when the column is wrapped in a function/cast or transformed in a way that doesn't match the available index.

Suspicious:

```sql
WHERE LOWER(email) = LOWER(:email)
```

without a matching expression strategy.

Potential solutions:
- normalize data at write time
- expression index
- appropriate collation/data type
- query rewrite

Do not rewrite solely for theoretical "sargability"; inspect the actual plan/workload.

---

## 18. OR / IN / Large Filters

Large dynamic filters can create:
- big parameter payloads
- expensive planning
- inefficient scans
- poor selectivity

Review whether:
- a join to a temporary/staging relation
- batch operation
- indexed lookup
- dedicated search design

would be more appropriate.

Avoid generating giant SQL strings from user input.

---

## 19. Aggregation

For expensive `GROUP BY`, `COUNT`, window functions, or reporting:
- identify how many rows are scanned
- check whether filtering can happen earlier
- check whether required indexes/order reduce work
- determine whether a precomputed/read model is appropriate

Do not move every aggregation into application code. That may increase data transfer and memory use.

---

## 20. Caching

Caching is an optimization, not a diagnosis.

Only introduce it when:
- the expensive operation is understood
- repeated access exists
- freshness requirements are defined
- invalidation is implementable
- cache key scope is correct
- stale behavior is acceptable
- cache failure has a safe fallback

A cache can hide poor SQL while creating consistency bugs.

---

## 21. Query Result Size / Egress

A query may be "fast" but still expensive because it transfers huge amounts of data.

Measure:
- number of rows
- selected columns
- large field sizes
- repeated requests
- aggregation done in application
- duplicated parent columns from joins

Optimize data movement, not only database execution time.

---

## 22. Connection Pooling

Sometimes "slow queries" are actually requests waiting for a database connection.

Check:
- pool size
- wait time
- active connections
- transaction duration
- leaked/idle transactions
- application concurrency

Do not increase pool size blindly; too many concurrent DB connections can increase contention and memory pressure.

---

## 23. Database vs Application Bottleneck

Classify the bottleneck before changing SQL:

```text
High DB execution time
    → query/plan/data/index problem

Low DB execution time
High API latency
    → app/network/serialization/external dependency

High query count
    → N+1/data-access pattern

High bytes transferred
    → projection/pagination/join/egress problem

High connection wait
    → pool/concurrency problem

Large planning time
    → query complexity/prepared-plan/design issue
```

The right fix depends on which category is actually dominant.

---

## 24. Query Rewriting

Before adding indexes, consider removing unnecessary work:
- fewer columns
- fewer rows
- fewer repeated queries
- earlier filtering
- avoiding unnecessary joins
- set-based operations
- batched reads

Query rewrite often has broader benefits than adding a specialized index.

---

## 25. Index as a Last-Informed Step

If the bottleneck is genuinely an index-access problem:
- inspect existing indexes
- evaluate selectivity
- design column order from predicates/order
- consider partial/expression/index-inclusion options
- measure write overhead
- verify the planner uses/benefits from the index

Use the sibling `database/indexing` skill for index-specific design.

---

## 26. Production Verification

After an optimization:
1. rerun representative workload
2. compare execution plan
3. compare latency
4. compare rows/bytes transferred
5. test different parameter distributions
6. check write impact
7. check concurrency
8. verify query results are identical unless behavior intentionally changed
9. document the reason for the change

Do not report "optimized" without before/after evidence.

---

## 27. Safety With EXPLAIN ANALYZE

`EXPLAIN ANALYZE` executes the statement. For mutating statements, this can change data.

Use caution:
- prefer read-only/select analysis
- use an explicit transaction and rollback only when safe/appropriate
- use a representative non-destructive equivalent for destructive operations
- understand triggers/side effects

PostgreSQL documents this caveat directly. citeturn851007search5

---

## 28. Common Anti-Patterns

### Index First
Adding an index before finding the bottleneck.

### Seq Scan = Bad
Forcing index usage on queries where scanning is cheaper.

### SELECT *
Fetching large/unneeded columns.

### No LIMIT
Returning entire tables through application endpoints.

### ORM N+1
Assuming elegant object access means one SQL query.

### Cache First
Hiding a bad access pattern behind a cache.

### Optimize One Parameter
Making a query faster for one lucky parameter distribution while worsening the common case.

### Plan Forcing
Changing planner settings before understanding statistics/query design.

### Production EXPLAIN ANALYZE Without Care
Executing expensive/mutating statements with ANALYZE without considering side effects.

## Review Procedure

1. Capture the real query/workload and baseline.
2. Inspect generated SQL and execution plan.
3. Compare estimated vs actual rows.
4. Review scans, joins, sorts, loops, buffers, and application query count.
5. Identify the dominant bottleneck.
6. Apply the smallest justified change.
7. Re-measure correctness, latency, and resource impact.
